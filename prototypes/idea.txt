New idea stemming from this: What if we have a "lossy" reversible algorithm that converts values 2^N -> 2^N-1, or 2^N - x that is x smaller than the original. call the 2^N set Q and the 2^N-x set P. we have some function that takes an address or number or value y in representation P to one of multiple representations in Q, but the encoder and decoder know what happened:

encoder:

takes data in representation Q and chunks it up into 16 uniquely identifiable chunks (This is important, no 2 chunks can be identical in the Q representation that are present in the list of chunks, so if its integers 4055 and 4055 could not be allowed to be in the same list of chunks for the algorithm to work). Then it runs these through the algorithm Q -> P. it results in 9 chunks or whatever in representation P with duplicates.

so you have like chunks Q[1, 2,  ... 15, 16] -> P[1, 2, ... 3_8, 4_9] < where the duplicates in P are prefixed. because the encoder took the time to carefully ensure that no chunks in Q are duplicate information the decoder can take advantage of that fact.

Decoder:

The mapping was something like 4 -> 1 in Q -> P and the reversible alrogrithm is uniformely probablistic to generate 1/4 outputs from 1->4 P -> Q. the decoder is smart enough to know from the encoding P[1, 2, ... 3_8, 4_9] hey I am supposed to see 3 separate reperentations of 8 and 4 representations of 9 in the Q output. so for 9 I just run until i get all 4 versions, and for 8 I run until i get 3/4 and have some probabilty of the 3 versions being right.  

say chunk 13, 14, 15, 16 all get mapped to 4_9, the ordering of the data is lost. unless we add some sort of ordering metadata inside of the chunk it self so like a checksum for the whole list, so 13 is actaully 13' with the ordering. the metadata lives in the representation that goes through the compression so it doesn't end up on the other half. 

So the decoder has the burden of doing multiple runs but selectively until it gets the probability right, and things like checksum could be done in parallel since checksum is a massivelly lossy compression technicall and is also non reversible it could be metadata that crosses the boundary. This is all veery algorithmic and I think I know where it falls apart. in a very large number or even reasonable computer values: Doing like 2^32 -> 2^30 so like a 4 -> 1 mapping (some rule has to exist to do this) you still have the problem of having 2^32 possible numbers, even after mutation if your sequence is only 16 numbers in Q (2^32) the resulting list is also so large that you probably don't get that lucky and the list in P (2^30) is just 16 chunks long, and now you have no compression and an annoying probability guess and check sequence to run through, so the mapping would have to be significantly more aggressive like 16 -> 1 or 24 -> 1, but then the burden is on the computation (and that might be where it falls apart).
